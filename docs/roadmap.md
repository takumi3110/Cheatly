# Cheatly 方向性・ロードマップ

## コンセプト

**万人向け。「コマンドを検索するより、このアプリを使った方が速い」状態を目指す。**

- 想定ユーザー: 初心者〜万人（コマンド名を覚えていない人を含む）
- 価値の核: 高頻度なコマンドに「その場で・確実に・コピーまで」最速で到達できること

## 基本方針

### 1. ゴールは「網羅数」ではなく「検索より速い」

- コマンドのロングテールは実質無限。埋めきろうとすると終わらず、品質も落ちる（フラグ1個の誤りは検索より悪い）。
- 質問の約8割は高頻度な「頭」に集中する。**頭で圧勝し、レアな「尾」は潔く手放す**ことで "検索より速い" は成立する。

### 2. 万人向け最大の壁 =「みんなコマンド名を知らない」

- プロは `du` を知っているが、初心者は「容量」「ディスク 空き」で探す。ここでヒットしないと、その瞬間に検索へ逃げられる。
- 勝負を分けるのは **コマンド数ではなく「タスクの言葉 → コマンド」のマッチング精度**。
- 既にある `kw` フィールドを、**人が実際に打つ言葉・質問の形**で厚くするのが最重要。

  | 弱い kw | 強い kw（万人向け） |
  |---|---|
  | `du 容量 使用量` | `du 容量 使用量 重い どのフォルダ 圧迫 空き 足りない ディスク` |

### 3. 深さより「ツールの種類（ロースター）」を広げる

- 1ツールを深掘りするより、対応ツールを増やす方が "検索より速い" の適用範囲が広がる。
- 目安: **1ツール 60〜80 コマンドで頭打ち**。その予算をツール数の拡張に回す。
- Linux は現状 50。`crontab` / `journalctl` / `zip` / `ss` などを数個足して 60 台で「完成」とし、次は別ツールへ。

### 4. 「やり方」系はレシピで奪う

- 「ポートを使っているプロセスを見つけて殺す」のような**タスク単位**の質問は単体コマンドでは拾えず、今も検索が勝っている領域。
- `recipe` 型（複数コマンドの組み合わせ）を用意して、検索の一番おいしい部分を奪う。

## 「完成」の定義（自分を縛るベンチマーク）

> **よくある質問 20 個で「アプリで探す時間」vs「検索で探す時間」を実測する。**

- 負けている質問が、次に直すもの。感覚ではなくデータで "検索より速い" を証明していく。
- 将来的には「アプリ内で検索して見つからなかった語」をログし、実データで次に足すコマンドを決める。

## 優先順（今後の実装順）

1. **kw をタスク言葉で強化** — 既存 50 コマンドを "検索より速い" 仕様に底上げする。一番コスパが高い。
2. **`recipe` 型を設計** — 検索が最強の「やり方」領域を奪う。
3. **ツール数を拡張** — 万人が触るツール（git, docker, npm/yarn, ssh, bash, kubectl, brew など）を増やす。

## 判断の指針（迷ったとき）

- 「コマンドを1個足す」より「既存コマンドが探せるようにする」を優先する。
- ロングテールを追わない。頭（高頻度）で確実に勝つ。
- 数を増やす前に、見つけやすさ（検索・kw・分類）が追いついているか確認する。
